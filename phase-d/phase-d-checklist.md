# Phase D Checklist

> Le spunte attestano quanto documentato nelle [schede di Fase D](phase-d.typ). Il report descrive cinque partecipanti, tre già coinvolti nella baseline. Le voci sulla partecipazione effettiva e sulla verifica dei dati grezzi restano aperte fino al riscontro sugli originali. Il test sommativo separato compare tra le attività future.

Riferimento: [specifiche complete](../docs/specs.md).

## 1. Team card

- [ ] Ripetere la Team card delle fasi precedenti senza variazioni non motivate. Il report presenta la scheda una sola volta, in Fase A.

## 2. Preparazione della valutazione

- [x] Identificare e congelare la versione da valutare.
- [x] Definire task e criteri di successo.
- [x] Riutilizzare, quando possibile, metodi e metriche della Fase A.
- [ ] Preparare schede, protocollo, dati attesi e responsabilità del team.
- [x] Distinguere chiaramente inspection interna e test con persone reali.

## 3. Inspection

- [x] Selezionare una o più tecniche pertinenti.
- [x] Eseguire un Cognitive Walkthrough passo-passo sui task principali.
- [x] Eseguire una Action Analysis quando serve quantificare le azioni.
- [x] Eseguire una Heuristic Analysis con guideline definite.
- [x] Far lavorare i valutatori separatamente quando previsto.
- [x] Consolidare i risultati in gruppo.
- [ ] Per ogni finding indicare versione, task, schermata e metodo.
- [x] Assegnare severità e priorità con criteri dichiarati.
- [x] Formulare raccomandazioni concrete.
- [ ] Correggere il prototipo.
- [ ] Documentare il passaggio tra versione iniziale e versione post-ispezione.
- [ ] Collegare ogni modifica della versione post-ispezione alla raccomandazione di Cognitive Walkthrough o Heuristic Analysis che l'ha originata.

**Deliverable:** Inspection card, schede individuali e changelog.

## 4. User testing del redesign

- [ ] Definire se il test è formativo o sommativo.
- [ ] Reclutare persone reali appartenenti ai segmenti.
- [ ] Coinvolgere almeno due partecipanti della sessione preliminare di Fase A.
- [x] Motivare l'uso degli stessi partecipanti o di partecipanti diversi.
- [x] Mantenere un intervallo adeguato tra test ripetuti.
- [x] Usare task confrontabili con quelli della Fase A.
- [x] Applicare metriche consolidate.
- [x] Includere almeno una misura di soddisfazione.
- [x] Eseguire un pilot del protocollo.
- [ ] Condurre i test senza guidare i partecipanti.
- [x] Compilare una Test Data card per ogni partecipante.
- [ ] Raccogliere successo, tempo, efficacia, errori, learnability e osservazioni.
- [x] Somministrare il SUS standard.
- [x] Inserire le tabelle quantitative nella documentazione.
- [x] Calcolare risultati individuali, media e varianza.
- [ ] Dichiarare deviazioni, limiti, bias ed effetto apprendimento.

**Deliverable:** Redesign User Testing card, card individuali, dati e SUS.

## 5. Iterazione formativa

- [x] Aggregare problemi quantitativi e qualitativi.
- [x] Costruire una curva d'urgenza.
- [x] Collegare ogni problema a una evidenza del test.
- [x] Prioritizzare le correzioni.
- [ ] Creare una nuova versione del prototipo.
- [ ] Aggiornare blueprint, wireframe, Before/After e Design card.
- [ ] Documentare tutte le modifiche nel changelog.
- [ ] Ripetere design e testing se i risultati sono ambigui o insoddisfacenti.

## 6. Valutazione sommativa

- [ ] Congelare la versione finale prima del test.
- [ ] Non modificare il prototipo durante la raccolta dati.
- [ ] Preferire partecipanti nuovi per limitare l'effetto apprendimento.
- [ ] Ripetere task, condizioni e metriche confrontabili.
- [ ] Calcolare risultati individuali e aggregati.
- [ ] Confrontare sistema originale e redesign.
- [ ] Separare risultati osservati e interpretazioni.
- [ ] Registrare anche risultati negativi o inattesi.

## 7. Conclusioni e raccomandazioni finali

- [x] Riprendere gli obiettivi iniziali.
- [x] Dichiarare ciò che il progetto ha raggiunto e ciò che non ha raggiunto.
- [ ] Sostenere ogni conclusione con dati e numeri.
- [ ] Interpretare i risultati senza generalizzazioni eccessive.
- [x] Confrontare qualitativamente e quantitativamente prototipo e originale.
- [x] Evidenziare punti di forza e debolezza.
- [x] Descrivere errori del team e relative correzioni.
- [x] Proporre attività future per aumentare affidabilità dei risultati.
- [x] Proporre eventuali miglioramenti funzionali.
- [x] Proporre ulteriori miglioramenti di usabilità.

**Deliverable:** Project Conclusion card.

## Controllo finale della fase

- [ ] Team card ripetuta nella fase. La scheda è in Fase A, Documento 01.
- [x] Versione valutata identificata senza ambiguità.
- [x] Inspection documentata.
- [ ] Test svolti con persone reali.
- [ ] Almeno due partecipanti provengono dalla Fase A.
- [ ] Metriche e SUS sono verificabili dai dati grezzi.
- [x] Tabelle quantitative incluse nella documentazione.
- [ ] Iterazioni motivate dai risultati.
- [x] Confronto finale con il sistema originale completato.
- [ ] Conclusion card completa di risultati, limiti e lavoro futuro.
